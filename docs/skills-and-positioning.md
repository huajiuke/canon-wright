# Canon Wright · 技术补齐与简历定位

> 配套文档：[产品宪法](product-constitution.md)（产品共识）。本文档解决另外两件事：**要补哪些技术**、**这个项目如何变成简历资产**。
> 状态：理念阶段，未开工。

## 1. 技术补齐全景

### 1.1 必补（挡住 MVP 的就这五个）

| 能力 | 为什么这个项目必须有它 | 从哪里入手 |
|---|---|---|
| 异步与流式 | 长篇生成几十秒起，没有流式输出连等待都受不了；并发调用、取消、超时都需要 | asyncio 的取消与超时语义、`StreamingResponse`、`sse-starlette` |
| 上下文工程 | 全书几十万字装不进上下文窗口 | 无成熟教材，靠实验 + 记录 token 数据（预算分配、滚动摘要、按场景组装、prompt 缓存） |
| 结构化输出与校验 | 卡片/缺口/回检报告必须机器可读，否则全是解析地狱 | Pydantic v2 严格模式 + JSON schema + 失败重试 |
| 检索实操 | 需要"引用到具体段落"，而不是"感觉相关" | SQLite FTS5 起步；重点不是选向量库，而是**切分策略**（按章/场景切，不按固定 token 切） |
| 评估与回归 | 唯一能把"感觉变好了"变成可验证的手段 | 20–50 条真实任务 + 期望要点，改 prompt 前后各跑一遍 |

### 1.2 次补（V1 之后）

- **确定性校验的工程化**：人名一致、时间线顺序、禁用词、字数这类能用规则判定的，**不要交给模型**，用正则/状态机/约束检查（参考 `QianBi-Novel` 的 must 契约思路）。
- **版本与 diff 的数据设计**：想清楚存全量快照还是存补丁、如何回滚。
- **可观测性与成本**：调用日志、token 计费、prompt 版本化、失败重放。
- **载体技术（三选一，不要都学）**：Codex 技能包（只写 `SKILL.md` + 脚本，零前端，最省）｜Obsidian 插件（TypeScript + esbuild + Obsidian API）｜桌面应用（pywebview 或 Tauri）。

### 1.3 写作侧领域知识（非技术，但同等关键）

- **结构理论**：三幕、**场景-续景（Scene/Sequel）**、故事问题、角色弧——产品字段（beat、弧、伏笔台账）直接建立在它们之上，不读的话 canon 表结构一定设计歪。
- **视角与人称一致性规则**：最容易规则化校验的一类，值得优先定义清楚。
- **做法**：认真读一本技法书，把它当作字段设计依据，而不是凭感觉建表。

### 1.4 明确不必学

微调 / LoRA、多 agent 编排框架（LangGraph/CrewAI）、向量库调优、K8s 与分布式多租户。单用户本地应用全用不上，学了也讲不深。

**补齐顺序**：上下文工程 → 结构化输出与校验 → 检索 → eval。不要先去学编排框架。

## 2. 简历叙述框架

### 2.1 先说风险

个人创作工具天生缺"规模"：没有并发、多租户、线上流量、SLA。直白写成"我做了个 AI 写作工具"，很容易被归为玩具项目。

### 2.2 破局：改叙述，不改项目

- **对外名称用「长文本一致性 Agent 系统」**，小说只是压力场景（超长上下文 + 强一致性 + 结构化输出）。
- **迁移语境**：合同审查、法规比对、医疗记录、客服知识库——同样面对"长上下文 + 强一致"。
- **四条可量化能力**（简历正文）：
  1. 上下文工程：把 N 万字长篇装进有限窗口（分层摘要 + 按场景召回 + prompt 缓存），token 消耗降低 x%
  2. 质量保证：确定性规则 + 模型审查的双层校验，回检准确率 / 误报率
  3. 检索：混合召回（全文 + 向量）+ 段落级溯源，命中率
  4. 数据模型：canon 版本化与可回滚设计

### 2.3 面试深点（每个准备 2 分钟）

1. 为什么是"缺口驱动"而不是"推荐流"——需求信号是怎么获得的
2. 上下文分层与摘要策略的取舍
3. 确定性校验与模型校验的边界如何划分

再加一个"踩过的坑 + 怎么用数据发现"的故事。

### 2.4 最强加分项

**真的在用**：能说出"连续用了 4 个月、写完 30 章、卡片引用率多少"，比功能清单强十倍。开源 star 是锦上添花，别为它加功能。

### 2.5 时机

等 M1/M2 跑起来、有真实数字之后再写进简历。现在写只能是空话，面试官一追问就露底。

## 3. 指标台账（从第一天起记录）

| 指标 | 为什么重要 | 来源 |
|---|---|---|
| token 消耗 / 单章成本 | 长篇高频调用，成本是硬约束 | 调用日志 |
| prompt 缓存命中率 | 直接决定成本与延迟 | 调用日志 |
| 检索命中率 / 段落级溯源准确率 | 决定"读到的能不能用上" | 人工抽查 |
| **卡片引用率** | 产品唯一硬指标：知识库的价值所在 | 卡片引用次数 |
| 回检准确率 / 误报率 | 决定回检功能是否值得信任 | 人工标注 |
| diff 采纳率 | 衡量 AI 产出是否真有帮助 | 采纳记录 |
| 连续使用周数 / 完成章数 | 最有力的"真在用"证据 | 使用记录 |
